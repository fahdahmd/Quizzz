# Quiz Game Backend

A real-time multiplayer quiz game API. Players join a room with a code, questions
are pushed to everyone simultaneously over websockets, and answers score on speed.
Question sets are optionally generated by an LLM from a topic the host types in.

Built with Python, FastAPI, and SQLModel.

## Architecture

The codebase is split in two, and the split is the most important thing about it.

```
engine/   Pure Python game logic. No FastAPI, no async, no I/O.
app/      Web layer: REST routes, websockets, persistence, AI.
```

`engine/` knows the rules — who can join, when answers are accepted, how points
are calculated, what order phases happen in. It has no idea a web server exists.
Every rule is enforced there and surfaces as a typed exception, which the web
layer maps to an HTTP status or a websocket error frame.

This means the rules are unit-testable without a server, without a network, and
without waiting for real time to pass. It also means a malicious client can't
reach an invalid state by talking to the API directly — the engine refuses
regardless of who is asking.

### Timing is server-authoritative

The server decides when a question opens and closes. A background `asyncio` task
per room drives the loop, measuring elapsed time with a monotonic clock. Clients
never report their own timing; they receive a deadline and a countdown.

Answers arriving slightly after the deadline are accepted inside a short grace
window and scored as if they landed exactly on it, so players aren't punished
for their own network latency.

### The AI is optional by design

Question generation was added last, after the game was fully playable. Every
failure path — no API key, timeout, malformed JSON, rate limit, too few valid
questions — falls back to a built-in question bank. A generation failure can
degrade the content but cannot break a game or prevent a room being created.

Model output is validated field by field before it becomes a `Question`; nothing
generated is trusted on the way in.

## Running it

### Locally

```bash
python -m venv venv
venv\Scripts\activate           # Windows
pip install -r requirements-dev.txt
copy .env.example .env
uvicorn app.main:app --reload
```

Interactive docs at http://127.0.0.1:8000/docs

### Docker

```bash
docker compose up --build
```

The container binds to `127.0.0.1:8000` only — put a reverse proxy in front of
it for anything public. A `Caddyfile` is included; Caddy handles TLS and
websocket upgrades with no extra configuration.

### Tests

```bash
pytest -q
```

The suite needs no network access and no API key. Timing tests run against
shortened intervals rather than real durations, so the whole suite finishes in
seconds.

## Configuration

All settings come from `.env` (see `.env.example`).

| Variable | Purpose |
|---|---|
| `QUESTION_TIME_LIMIT` | Seconds per question |
| `MAX_PLAYERS_PER_ROOM` | Cap per room |
| `ALLOWED_ORIGINS` | Comma-separated; enforced on websocket handshakes too |
| `DATABASE_URL` | SQLite by default; any SQLAlchemy URL works |
| `OPENROUTER_API_KEY` | Optional — omit to always use the built-in bank |
| `TRUST_PROXY_HEADERS` | Set true **only** behind a proxy you control |

`.env` is gitignored and must stay that way — it holds the API key.

## Protocol

REST creates rooms and issues player tokens. Everything during a game runs over
`WS /ws/{code}?token=...`. All messages are `{"type": ..., "payload": ...}`.

**Server → client:** `room_state`, `player_joined`, `player_reconnected`,
`player_left`, `question_start`, `answer_received`, `question_end`, `game_over`,
`error`

**Client → server:** `ping`, `state`, `start` (host only), `answer`

`question_start` never includes the correct answer. It is revealed only in
`question_end`, after the question has closed. `answer_received` confirms receipt
without disclosing correctness, so nobody learns the answer early.

Reconnecting with the same token restores a full state snapshot including the
current question and its remaining seconds. The previous socket is closed with
code 4409.

## Security notes

- Room codes and tokens come from `secrets`, not `random`
- Tokens are opaque — they encode nothing and can't be forged by editing an ID
- Websocket auth happens before `accept()`, so unauthorised sockets never open
- Origin is checked manually on handshakes; CORS middleware does not cover websockets
- Inbound websocket messages are size-capped before parsing
- Rate limits on room creation and joining, keyed by client IP
- Unhandled errors return an opaque ID; tracebacks go to logs only
- Room and token records are swept after 30 minutes idle

## Known limitation: single process

All room state — connections, timers, scores — lives in one process's memory.
Running multiple workers would give you several servers that each know about
different games, and players would land on whichever one the load balancer chose.

**Do not run this with `--workers`.** One process handles a few hundred
concurrent players comfortably.

Scaling horizontally means moving room state into Redis and broadcasting through
Redis pub/sub so any worker can reach any player. That's a real piece of work,
not a configuration change.
